We are build a Javascript version of the game Dune by Cryo in order to be able to run it on all modern machines with a web browser. The original game was a DOS game and the full source code is not available. In the workspace, there is a C# and asssembly project that is an attempt to reverse engineer some of the game. Cryogenic replaces x86 assembly routines in the DOS executable DNCDPRG.EXE with C# methods. Spice86 runs the original binary and redirects execution to the C# overrides at registered addresses. Assembly and C# code share the same emulated memory, so overrides can be introduced one function at a time without breaking the rest of the program.
The SHA256 of the required DNCDPRG.EXE (Dune CD version 3.7):
5f30aeb84d67cf2e053a83c09c2890f010f2e25ee877ebec58ea15c5b30cfff9
The game files (DNCDPRG.EXE, DUNE.DAT) are present in the directory. All the sprites, music, video, dialogues, palette assets are coming from DUNE.DAT.
The full details of the Cryogenic project are available in README.md.
We are writing our rebuild in the directory Rebuild. The Assets extractor is a tool we wrote to extract the assets from DUNE.DAT in order to prepare them for the Javascript execution engine.
The directory scummvm-cryo contains the source code for an attempt at porting Cryo games into scummVM engine. It is not 100% compatible with Dune but can contain useful code to understand some of the mechanics.
The directory swift-dune contains a swift implementation of the engine. It is written in Swift 5.6 and runs on macOS. It can be used for inspiration There are 2 applications: 1) Editor view: used to browse the assets, 2)Game view: play the game.
During our reverse engineering attempts, we documented the effort with documentation files in the directory Rebuild/DOCUMENTATION/Tech. As you are making progress in this project, always ensure the documentation is up-to-date and refreshed with any new findings.
The directory OpenRakis contains an older re-implementation attempt.
We build a full assets extractor here Rebuild/asset-extractor, to extract all the assets from the DUNE.DAT file and prepare them for the runtime execution in the Javascript engine.
An assets viewer is present in the directory Rebuild/viewer to help the user to visualize the extracted assets as they have been prepared for the game runtime.
The main game runtime is in this directory Rebuild/game.
When making progress toward the runtime development, if assets extraction needs to be modified to produce better shaped assets or companion files for the runtime, that's OK to modify the assets extraction process to prepare as much as possible the assets upfront for real-time execution.
When implementing the game mechanics, use the existing .asm and port to JS as much as possible. The key is to create a faithful port of the game so we want to stick as much as possible to the original implementation and use the assembly or C# rewrite when possible to translate them into JS.
We build a Spice86 test harness documented here Rebuild/DOCUMENTATION/Tech/29-trace-harness.md to facilitate the retro engineering tasks and capture what we need to replicate the exact behavior but try to rely as much as possible on the static analysis of the existing code dumps in the Cryogenic engine. It's better to reverse engineer the existing dumps even if it's a larger effort and rely on the harness only for things that cannot be detected with static analysis.
